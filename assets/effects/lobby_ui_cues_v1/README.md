# Lobby and loading UI cue candidates

Eleven original procedural cues, generated by `tools/generate_lobby_ui_cues.py`.
No recorded or existing audio samples are reused. The source uses damped body
modes with short filtered-noise attacks. A D5-centred body (587.33 Hz) relates
them to the existing select cue's measured 588 Hz dominant mode. The stock
select.wav lasts 0.306 s; button_hover_pcm.wav lasts 0.046 s. This set keeps the
same brief tactile family, with rising/falling gestures for state changes.
Timbre matching still requires subjective listening review.

| File | Intended trigger / gesture | Duration | Peak dBFS |
| --- | --- | --- | --- |
| player_joined.wav | Accepted lobby player join; rising pair | 0.200 s | -8 |
| player_left.wav | Displayed player departure; falling pair | 0.180 s | -10 |
| ready_on.wav | Ready enabled; rising confirmation | 0.180 s | -10 |
| ready_off.wav | Ready disabled; quieter falling undo | 0.160 s | -12 |
| team_change.wav | Confirmed team change; brief neutral click | 0.095 s | -12 |
| colour_change.wav | Confirmed colour change; lighter neutral click | 0.085 s | -13 |
| bot_added.wav | Bot slot added; short rising pair | 0.135 s | -11 |
| bot_removed.wav | Bot slot removed; short falling pair | 0.135 s | -12 |
| section_expanded.wav | Advanced section opened; quiet short tick | 0.065 s | -16 |
| section_collapsed.wav | Advanced section closed; quiet short tick | 0.060 s | -16 |
| all_players_ready.wav | Loading ready-up actually complete; brief three-note confirmation | 0.370 s | -6 |

All files are mono 44.1 kHz, 16-bit PCM WAV, one-shot playback. Quiet disclosure
clicks are deliberately lower than readiness/join confirmations; the all-ready
chime is brief rather than a fanfare. The manifest stores exact encoded levels,
seeds, note schedules, spectral metrics and SHA256 hashes. Source file levels
are not a replacement for the existing Master/SFX/menu audio settings.

## Integration notes

This package does not change Lobby, LoadingScreen, Sfx or match state. Claude
should map cues to confirmed existing state changes after acceptance. Do not
play notifications while rebuilding UI controls or on every readiness poll.
The all-ready chime belongs to the actual completion of the loading ready-up,
not initial scene construction. Review existing select/hover hooks so an action
is not double-played. Preserve current settings and state authority.

## Validation and reproduction

Run `python tools/generate_lobby_ui_cues.py`. All eleven actual WAV containers
passed mono/rate/bit-depth and byte roundtrip checks. Durations are 0.060..0.370 s,
peak targets -16..-6 dBFS, no clipped samples, zero first/last samples, DC below
1e-5 and quiet final 20 ms. Eleven hashes are distinct and unchanged after
regeneration. Generator syntax and diff checks pass. No game/engine/test suite,
benchmark or automatic playback was used.

See `docs/art_mockups/lobby_ui_cues_v1/waveform_review.png`, `audition.wav` and
`audition_timeline.json`. Audition preserves stored levels with 700 ms gaps.
Waveforms were inspected; listening, cue recognition, fatigue and actual in-game
mix remain Claude/owner acceptance. These are asset candidates, not live UI proof.
