## 1. Diagnosis (file:line, root causes)

**85.33 white models (high confidence, not the carrier).** In `screenshot_..._203632.png` the white bomb floats at the cursor with "HELD: Bomb" in the HUD and no shadow: it is the held-gift GHOST, not a dropped carrier. `GhostPreview._apply_gift_tint` (game/GhostPreview.gd:714-732) puts an UNSHADED alpha overlay on every mesh of the GLB (`material_overlay = _gift_tint_material`, :731). For the plain valid state 1pi.85.16 replaced the owner colour with `GIFT_NEUTRAL_TINT = Color(1,1,1,1)` (:703, :727), so valid = a 55%-alpha white unshaded wash over charcoal/dark models (GLB albedos are linear 0.02-0.1, e.g. bomb "Charcoal shell"), i.e. plain white. The HUD icon is a pre-rendered PNG, hence dark red. GLBs themselves are fine (no textures, plain PBR factors, metallic 0). Fix: valid state sets NO overlay (`material_overlay = null`); keep the overlay only for invalid/hole/locked/throw cues; glow rim stays. The world carrier has no overlay (BlockFactory.apply_gift_visual:168-206; GiftBlink overlay is red 0.55 alpha, GiftBlinkTuning), so it should render correctly; the worker confirms with one gift-demo capture of a dropped carrier.

**85.24 activated gifts drop a body.** Every gift goes `MatchPlacement.request_place` -> `_spawn_block(..., gift_id)` (autoload/match/MatchPlacement.gd:264) -> `_attach_pending_special` (:299): a physical carrier is spawned, falls, lands, then the effect starts. Stackfall triggers on impact and the carrier lingers `gift_despawn_delay_s` (SpecialBehavior.trigger, `_despawn_timer`); Earthquake keeps the carrier on the disc for the whole 4 s shake (EarthquakeEffect.wants_early_trigger); Volcano waits `needs_landing()` (VolcanoEffect.gd, `needs_landing -> true`) before spawning its structure. Root cause: these three effects only need a position/owner but are bound to a falling `Block`.

**85.25 Paintball/Rocket gravity (likely, two causes).** (a) The carrier spawns at the ghost (hover 0.3 m above the surface), `arm_delay = 0.4` (rocket.tres/paintball.tres) means `RocketEffect.physics_tick` (RocketEffect.gd:126) and `PaintballEffect.physics_tick` (PaintballEffect.gd:45) do not launch until 0.4 s later (`SpecialBehavior.advance`, :120-146): the carrier falls at `gravity_multiplier 1.4` (physics_tuning.tres), usually lands, and then "launches" along the camera forward whose downward part is kept (`RocketEffect.sanitize_launch_direction` only strips upward) so it scrapes along the disc. (b) Flight is velocity-held every tick (`block.kick(direction * thrust)`, :133) but `gravity_scale` stays 1.4, so each tick adds gravity before the next write; thrust 14 m/s is also slow. Rocket orientation: nothing writes the basis (`block.angular_velocity = Vector3.ZERO`, :134 only), the GLB stays upright.

**85.26 black hole destroys nothing.** Different cause from fca.40. fca.40 is a bench race (client listener after PLAYING). In a real host match `Match.registry()` exists, so `HoleDissolver.request_dissolve` (game/HoleDissolver.gd:154-161) succeeds and `start_dissolve` -> `_finish` -> `Field.remove_fallen_block` works (the translucent block in `..._203951.png` is a dissolve in progress). The pile is a capture-geometry problem: `RadialPull.pull` (game/specials/fx/RadialPull.gd:33-39) captures only when the 3D distance from the block ORIGIN (bottom face pivot of a possibly multi-cell shape) to the hole centre is <= `core_radius_m` 0.8 (black_hole.tres). The centre is the carrier's position; blocks arrive on the disc, jam into a ring/column (cube is 1 m, tetrominoes are longer), the pile grows UP and no block above the first layer or with an offset pivot ever gets within 0.8 m 3D, so most are pulled forever (`friction_compensation 24` keeps them pressed against the pile). Fix without touching RadialPull.gd (fca.40 lands there in wt/bh-race): BlackHoleField runs its own capture sweep (horizontal radius + height band + short hold) and passes an invalid `on_captured` to RadialPull.

**85.27 weak blasts.** `ExplosionFx.blast` (game/specials/fx/ExplosionFx.gd:16-37) is mass-aware already; the values are what is small: bomb radius 5 m / peak 12 / max 16 m/s, rocket 4.5 m / 10 / 16 on a 90 m disc with `falloff_exponent 1.5` (a block half the radius away gets about 35%). Pure tuning.

**85.28 Jumping Bean (likely, confirm in test).** Timeline today: `LandedProbe.update` (game/specials/fx/LandedProbe.gd:30-55) needs speed < 0.5 m/s for 0.2 s while touching, else the 5.0 s `landed_timeout_s` ceiling from first contact (LandedTuning.gd). A bean thrown on the fixed arc bounces/rolls (`block_bounce 0.4`) and on a tilting disc speed stays above 0.5, so "landed" arrives at the 5 s ceiling = the owner's "idle for 5 s". Then the first hop is only due at `landed_age >= hop_interval_s` 1.2 s (JumpingBeanEffect.physics_tick :76-88), so total idle 5-6 s. A hop is `UP*6.5 + 3.5 horizontal` (`_hop` :104-117) at gravity 1.4 g: apex 1.5 m, 3.3 m across, on a 90 m disc: "tiny"; the hole is `hole_radius_m 1.4` (jumping_bean.tres), about 6 cells, "very small", opened at the PRE-hop position; if the horizontal velocity is lost to the contact friction of the first step (kick is written while still touching the disc, `block_friction 0.85`) the bean lands back in its own hole and `HoleDissolver.touches_hole` (HoleDissolver.gd:206-) dissolves it ("despawn"). The cure is behavioural: bean-specific landing thresholds, first hop within about 0.4 s, bigger/farther hop, bigger hole, and a post-hop guard so the bean never dissolves in the hole it just opened.

**85.29 throwables: clunky.** Today a throwable needs hold-LMB drag (`_can_begin_throw_aim` PlayerController.gd:1045-1055, `_update_throw_aim` :1088, `_commit_throw_aim` :1191), a drag becomes velocity (`_throw_velocity_for_drag` :1233) and the host (`MatchPlacement.request_throw` :341-476) keeps only the heading and applies `GiftThrow.fixed_velocity` (core/gifts/GiftThrow.gd:30-37). Rocket/Paintball already use the camera forward (`_request_place` :965-970 -> `_request_throw(_camera_forward())`, host `sanitize_aim`, `_apply_aim_direction` :486). The owner wants the same camera-driven flow for Bomb/Magnet/Bean with a ballistic arc, active automatically (preview always on while held, plain click throws, no LT/drag).

**85.30 volcano particles.** `VolcanoStructure` (game/specials/VolcanoStructure.gd) builds cone/model and spawns blocks in `_erupt` (:287-307); there is no particle node at all. Add client-side GPUParticles3D in the same node (both host and client builds run `_ready`).

**85.31 random shapes.** `VolcanoEffect.block_shape`/`StackfallEffect.block_shape` are exports preloaded to `cube.tres`; `StackfallRain._spawn_one` (:~66) and `VolcanoStructure._erupt` (:302) pass that one shape to `BlockSpawner.spawn` (game/specials/fx/BlockSpawner.gd:10-22). `BlockShape.load_all_shapes()` (config/blocks/BlockShape.gd:100) already lists all 11 shapes.

**85.32 activation size.** Nothing scales a gift; `BlockFactory.apply_gift_visual` (game/BlockFactory.gd:168-206) is the single shared hook run by host and clients (via spawn RPC with `gift_id`), builds a 1-cell box collider and sets `block.mass = cube_mass`. Scale belongs there so no RPC is needed (same approach as GiftBlink).

## 2. Decisions recorded (minor)

- Instant activation uses a non-physical host-only "anchor" (a bare `Block` outside `blocks_parent`, never registered, `net_id = -1`, not replicated) so the effects keep their `Block`-typed API; removed on `completed`.
- Aimed/thrown projectiles spawn on the camera line: host spawn point = cursor point - forward * `gift_aim_back_m` (clamped >= `gift_aim_min_height_m` above the surface), so the line passes through what the player points at, no new RPC (client `origin` is the existing cursor pose, forward rides the existing `velocity` slot, host never trusts length/speed).
- Rocket keeps "not upward" (SPEC 2.6 owner row 2026-10-05); gravity 0 plus camera-line spawn is what makes it fly straight at the target.
- Activation scale is applied at release (spawn) on all peers from `SpecialDef.activation_scale` (release is activation in this game).
- Black hole capture is its own sweep in BlackHoleField; `RadialPull.gd` is not edited by this round.
- SPEC 2.5 "Throw (specials only)" drag-throw [ORIGINAL] is superseded by the owner's 2026-10-06 text; the orchestrator records it in the SPEC decision record (not done in this plan).
