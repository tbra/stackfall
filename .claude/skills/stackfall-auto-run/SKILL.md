# Auto-run Stackfall

Version: 1.1.1

Before acting, run `python tools/skill_versions.py --check stackfall-auto-run 1.1.1` and report its `Using ... (disk verified)` line to the owner. If it reports `STALE`, stop using this loaded copy, re-invoke the on-disk skill once, and start a fresh Claude session if the mismatch persists. List the versions of all three project skills with `python tools/skill_versions.py` at the start of an unattended run.

Use on the main orchestrator thread only after the owner activates continued work. The project's Git authority and pause points in `CLAUDE.md` still apply. Keep the orchestrator's context small: delegate implementation and long diagnostic loops; read brief results and decisive evidence, not whole logs.

Unattended context guard: keep working through ready, authorized packages; task counts and delivered batches are **not** stop conditions. Claude's native `autoCompactWindow` is the context backstop. At each delivered batch, leave a compact Bead checkpoint with the next exact action and active checkout/worker state, then continue. A context/compaction warning is a checkpoint signal, not a reason to end the session: secure in-flight work, let native compaction occur, reconcile from the checkpoint and live Git/Beads state, and continue. Use `stackfall-session-close` only when work is actually done or a real stop condition below prevents safe continuation. Do not claim that this skill can reset Claude's transcript or avoid the account's usage limit.

Keep main-thread Bash output small: request only needed file ranges and targeted matches; never print full logs, large files, whole-board JSON or broad diffs. Default to at most about 100 lines / 4 KB of command output per diagnostic, saving complete test/build output to the assigned scratchpad and returning exit status, totals, decisive errors and its path. For tests, preserve the original command's exit status rather than relying on a `head`/`tail`/`grep` pipeline's status. Expand a specific slice only when the concise result cannot decide acceptance. Worker contexts may inspect their own full logs.

At orientation, do not shell-dump `AGENTS.md` or skill files already supplied/loaded by Claude just to find their versions; use the version helper and read only missing relevant sections. Use `bd show <id> --json --brief-deps` for routine issue state, not full comment bodies. Read comments only for interrupted-work recovery, failed gates or disputed evidence. Give workers a plan path/section and concise acceptance criteria, not a pasted section the orchestrator already read. For GUT output, show the totals and unique decisive failures, collapsing repeated `Orphans` lines to a count plus one example; keep the full log on disk. Start review with `git diff --stat` and request only the decisive hunk. Bundle related small orientation queries when that avoids repeated tool-call overhead without creating a giant result.

1. Run `python tools/board_brief.py` for the bounded ready/in-progress overview; query individual beads only as needed. Do not print whole-board JSON into the main chat. Reconcile existing worker/checkpoint state before taking new work. Prefer a ready package that unblocks dependent work; keep the owner's current priority above stale handoff suggestions.
2. Inspect `bd show <id> --json --brief-deps` for the next bead without comment bodies, plus relevant source slices and required spec/plan. Search `bd memories <topic>` before repeating an unfamiliar investigation; use `bd search <topic>` to check whether feedback already has a bead. A triage worker may pass up to ten plausible results to `tools/rank_context.py` for a Jev relevance judgment; the board and source evidence still decide whether two issues are duplicates. Keep shortlists out of the main thread. Assign one outcome, exact checkout/base and disjoint files. Run `tools/route_model.py` for the dispatch verdict, then give the worker named checks, a time limit, run count, and visual-probe limit from `docs/AGENT_WORKFLOW.md`. The orchestrator logs the brief and verdict in Beads with `--actor stackfall-orchestrator`.
3. Have workers iterate within their budget, comment detailed findings on their assigned Bead, and return hook-validated compact JSON (1100 characters on success/review, 1500 on failure) with candidate, files, named checks, decisive finding and next action. Treat `record=bd:<id>` as durable recovery evidence, not an instruction to read the comment. Open it only for interrupted-work recovery, a failed gate or a disputed finding. Full logs stay in the assigned scratchpad. A budget expiry returns a recoverable checkpoint; it never counts as acceptance. Verify candidate identity, diff, test totals, and any required independent review. Inspect `git diff --stat`, `git diff --check` and scoped hunks first; give large diffs to the reviewer instead of dumping them into the main chat. Avoid duplicate worker and integrator test runs unless a concrete integration risk warrants them.
4. Commit only accepted, owned files; integrate them without overwriting unrelated state. Run the full GUT suite once per integrated game-code batch and any required specialized gate on the integrated revision. For tooling/docs, use focused checks. When green, push code immediately, verify the remote revision, record commit and gate evidence in local Beads, and close accepted package issues. Do not attempt Beads remote sync; no remote is configured.
5. Before every new dispatch, reconcile the brief checkpoint and any context warning as above, then continue while actionable work remains. Stop for `[ORIGINAL]` rule changes, owner decisions, art direction, exhausted quota, conflicting ownership, an unresolved failed gate, or failed context recovery that makes safe continuation impossible. Continue unrelated safe packages where possible. Do not endlessly retry a failed command.

Routine user updates are one useful line: bead, result/count, next action. Expand only for a decision, failed gate, or material risk. Use `stackfall-session-close` before ending a long run.
